Audit espace pilote — cohérence & bugs

2026-09-11 · après les chantiers paiement des annonces, garde-fous transverses et messagerie. Référence : questionnaire-espace-pilote-reponses.md (89Q, 06/09), plan-attaque-espace-pilote.html, projet.html. Périmètre : ce qui n'a pas été retranché par le pivot 08/09 (Blocs B/C/D gelés, pas de découverte légale, pas d'ouverture publique).

Verdict. Les parcours cœur fonctionnent (publier une annonce → demande → route → paiement virement → reçu → vol effectué → messagerie). L'intégration drawer admin ↔ pilote via viewerRole est saine : guards requireAdminOrOwningPilote partout, Q64 respecté (le pilote ne voit jamais les autres), aucun IDOR trouvé.
Restent 3 lots : A. emails du parcours annonce non « pilote-aware » (voix de Romain) · B. écarts questionnaire encore dans le périmètre (dashboard, carnet, consentement, cash, nav admin) · C. bugs potentiels — surtout la migration 20260911 non exécutée et le pilote désactivé qui laisse des réservations orphelines.

4 · Bugs potentiels

PZoneRisque
P0 Déploiement Migration 20260911_reservation_messages.sql non exécutée. Selects explicites sur reservations.messages_token, pilotes.signature et la table reservation_messages → PostgREST 400 → onglet Messages, page /reservation/messages/[token], champ signature, /pilote/profil cassés. Même classe que l'incident 08/09. 20260910 : exécutée en local, à exécuter en prod aussi.
P0 Q11 · désactivation pilote togglePiloteActif(false) ne dépublie que les annonces statut='publiee'. Une annonce reservee (client avec réservation demande_recue / payment_pending en cours) reste liée à un pilote inactif → réservation orpheline : le pilote inactif est refusé par requireAdminOrOwningPilote, l'admin peut agir mais rien ne le lui signale, et le client n'est pas prévenu.
P1 setPilotePaye Restauration : restored = pre_payment_statut || "heure_confirmee". Si le pilote a envoyé la route sans passer par « Confirmer le créneau », pre_payment_statut peut valoir demande_recue → une réservation payée reste affichée demande_recue. Fix : forcer un statut avancé au moment de cocher « payé ».
P1 respondToRouteProposal (annonce) Le select imbriqué route_proposals → reservations → pilotes(nom) (commit 1637da5) repose sur la FK reservations.pilote_id → pilotes. tsc + build OK mais à vérifier en runtime : si PostgREST ne résout pas le chemin → piloteNom vide dans l'email virement, ou 400.
P1 AnnoncePiloteActions optimiste Sur « le client m'a payé », l'UI appelle onStatusChange(id, "heure_confirmee") en dur — peut différer du statut réellement restauré. Cosmétique tant que le drawer se recharge, mais le badge de la liste peut mentir jusqu'au reload.
P2 /api/pay-qr/[id] Public, pas de rate-limit ; le QR encode l'IBAN du pilote. UUID non devinable → risque faible, mais un lien fuité expose l'IBAN à qui décode le QR.
P2 Mode « place » — CAS /api/vol-annonce/submit fait un compare-and-swap .eq("places_reservees", prev). Si un décrément a lieu entre le fetch et l'update, le CAS échoue et renvoie « ce vol vient d'être réservé par quelqu'un d'autre » — message trompeur. Fix : « réessayez », ou relire + retenter une fois.
P2 isPiloteVol élargi Désormais toute résa type_resa='standard' avec pilote_id sort du CA (lib/transactions.ts). Bloc B gelé → aucune résa standard n'a de pilote_id aujourd'hui, donc inerte ; mais une donnée de test qui traîne disparaîtrait silencieusement des totaux. Vérifier en base : select pilote_id, type_resa from reservations where pilote_id is not null.
P2 /api/inbound-email Codé, route publique, répond 200 à tout — inerte tant qu'il n'est pas branché. Si branché sans INBOUND_EMAIL_SECRET, n'importe qui peut injecter un message dans un fil en connaissant un messages_token. Fix : rendre le secret obligatoire (400 si absent) avant de brancher.

5 · Intégration admin ↔ pilote

Saine dans l'ensemble. Le ReservationDrawer unique piloté par viewerRole :

  • ActionFooter masque encaissement / lien Stripe / relance / NewCAG / « vol effectué » générique côté pilote ; ModifierTab read-only ; MessagesTab et AnnoncePiloteActions ouverts aux deux rôles avec guard serveur requireAdminOrOwningPilote.
  • /admin/vols et /pilote/vols chargent tous les deux select("*") → mêmes données ; messages_token / pilote_paye / mode_vente remontent sans select explicite (pas de risque 400 côté liste).
  • L'admin peut agir sur une annonce (marquer payé, vol effectué sans verrou 8 h, répondre dans le fil) — cohérent avec Q88 (admin = contrôle total).
  • /admin/transactions : annonces exclues de la P&L, section séparée — conforme Q45/Q46.

Points de friction :

  • Le compteur de changements de créneau n'existe que dans le drawer, pas d'écran « stats par pilote » agrégé (Q67) — hors périmètre Bloc B, mais Q67 le voulait.
  • Aucun signalement admin quand une annonce/réservation devient orpheline (§4, P0 Q11).
  • /admin/pilotes : la désactivation affiche le récap releasedFlights / unpublishedAnnonces mais ne compte pas les réservations d'annonce actives.

Suite proposée

  1. P0 tout de suite : exécuter 20260910 + 20260911 en prod (Romain) · étendre la cascade togglePiloteActif(false) aux réservations d'annonce actives (annuler + email client + compter).
  2. P1 par lots : dashboard pilote (2 compteurs) · carnet « vols passés » · consentement partage de données (décision Romain d'abord) · fix setPilotePaye · vérif runtime respondToRouteProposal.
  3. Emails pilote-aware : fondu dans la refonte des ~32 emails (backlog), pas un chantier séparé.
  4. P2 en finition : option cash · nav admin « Équipe » · Modifier éditable pour les annonces · email « paiement confirmé » · message d'erreur CAS · secret inbound obligatoire.
