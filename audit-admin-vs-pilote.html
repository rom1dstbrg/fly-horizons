Audit admin ↔ pilote — vers « tout passe par l'espace pilote »

2026-09-14 · Point de départ : Romain veut qu'à terme /admin ne serve plus qu'à administrer le site, et que toute création de réservation (standard + vol sur mesure) passe par l'espace pilote, avec des capacités différentes selon le pilote. Lui-même, admin et pilote, doit pouvoir tout faire. Ce document répond à « est-ce possible ? » avec l'état réel du code — aucune ligne de code écrite à ce stade, on prépare le plan. Indexé depuis projet.html.

Verdict court : oui, c'est possible, et le périmètre réel est plus petit qu'il n'y paraît. Sur les 18 sections de /admin, une seule (reservations/*, création + gestion) est vraiment concernée par la bascule — le reste (boutique, clients, transactions, réglages, analytics, roster des pilotes...) est déjà légitimement de l'administration pure et n'a aucune raison de bouger. Le vrai blocage n'est pas fonctionnel, il est dans le modèle de rôle.

La décision du 13/09 (« Romain republie son catalogue via /pilote/annonces ») supposait implicitement ce jonglage entre comptes, sans le dire explicitement.

Le modèle de rôle est un enum unique, pas un ensemble de permissions

profiles.role vaut 'customer', 'admin' ou 'pilote' — un seul à la fois. middleware.ts et les deux layout.tsx (admin/pilote) vérifient une égalité stricte : role==='admin' pour /admin, role==='pilote' + une ligne pilotes avec statut='actif' pour /pilote. Un compte ne peut physiquement pas être redirigé vers les deux — même si en dessous, la couche des server actions est déjà plus permissive (voir plus bas).

Bonne nouvelle : la couche autorisation est déjà à moitié prête

lib/actions/auth-guards.ts expose déjà requireAdminOrActivePilote() et requireAdminOrOwningPilote(reservationId), utilisés dans ~8 fichiers d'actions (édition de réservation, messagerie, attribution pilote, paiement, itinéraires, masse & centrage, mise en jeu de vols). Le principe « admin OU pilote actif peut agir » existe déjà pour gérer une réservation existante. Il n'existe simplement pas encore pour la création.

Le vrai trou : aucune des 3 créations admin (réservation, hors-site, vol sur mesure) n'utilise le guard combiné requireAdminOrActivePilote — elles sont toutes en checkAdmin() strict. Et « annonce pilote » écrit dans une table différente (annonces_pilote), ce n'est pas un mécanisme générique de « pilote crée une réservation », c'est un système à part.

Vol sur mesure : hors périmètre historique. plan-attaque-espace-pilote.html (projet Bloc A/B/C/D, attribution de pilote) le dit noir sur blanc : « vol sur mesure (type_resa=perso) — non concerné par l'attribution [v1] ». Construire une création de vol sur mesure côté pilote n'est pas la reprise d'un chantier existant, c'est un vrai chantier neuf.

Ce qui bloquerait une bascule complète

  1. Le rôle unique — voir plus haut, c'est le blocage racine.
  2. Aucun niveau de capacité entre pilotes — la table pilotes n'a aucune colonne du genre « peut créer une réservation ». Tous les pilotes actifs ont exactement les mêmes droits aujourd'hui. Ta demande (« selon le rôle, ils peuvent ou non ajouter ») veut dire créer cette notion de zéro.
  3. Aucune UI/action de création côté pilote — ni réservation standard, ni vol sur mesure. À construire, pas à réactiver.
  4. Fuite déjà documentée : ActionFooter (le pied du tiroir réservation) ne connaît pas viewerRole — un pilote peut voir/cliquer des actions admin-only (encaisser, boarding pass, proposer un créneau) si elles ne sont pas filtrées une par une. Étendre les pouvoirs des pilotes sans corriger ça rouvre ce trou.
  5. Sécurité 100% applicative, pas de RLS réelle — les tables pilote/réservation ont des policies using(true). Chaque nouvelle capacité doit être vérifiée à la main dans le code serveur, sans filet ; un oubli est une vraie fuite de données, pas juste un bug d'UX.
  6. Dette annexe sans rapport direct mais qui alourdit toute modif : checkAdmin() est copié-collé dans 18 fichiers au lieu d'être un helper partagé.

Cadre légal / périmètre à respecter (déjà tranché, ne pas rouvrir)

  • Le cadre NCO.GEN.104 (partage de frais) reste la base légale de tout l'espace pilote — un pilote qui crée une réservation doit rester « il organise son propre vol », pas « Fly Horizons lui envoie du travail ».
  • Pas de recrutement, pas de page « postuler », pas d'ouverture à des pilotes inconnus — décision déjà actée. Un système de capacité par pilote doit rester une bascule manuelle par toi sur un roster que tu connais, pas un système d'auto-élévation.
  • Pas de Stripe Connect / paiement centralisé — chaque pilote continue à encaisser lui-même (virement/QR), même si la création de la réservation se fait depuis l'espace pilote.

Plan proposé, par phases

Phase 1 — Résoudre ton propre confort (un compte, deux casquettes)

Aligner le routing sur ce que la couche action fait déjà : accès à /pilote/* basé sur « a une ligne pilotes active », indépendamment de profiles.role — plutôt que sur une bascule complète vers un système de rôles multiples (plus gros chantier, pas nécessaire pour ce problème précis). Concrètement : tu pourrais fusionner tes deux comptes (ta ligne pilotes pointe vers ton compte admin) et accéder aux deux espaces avec un seul login. C'est isolé, sans effet sur les autres pilotes.

Phase 2 — Niveaux de capacité par pilote

Nouvelle colonne sur pilotes (ex. peut_creer_reservations boolean, défaut false) + bascule dans /admin/pilotes (déjà existant). Roster géré à la main, cohérent avec la décision « pas d'auto-élévation ».

Phase 3 — Création côté pilote (réservation standard)

Nouvelle action serveur (variante de createAdminReservation) gardée par « admin OU pilote avec peut_creer_reservations=true », nouvelle page sous /pilote/*. Réutilise le pattern auth-guards.ts déjà en place côté édition.

Phase 4 — Vol sur mesure côté pilote

Chantier neuf (voir plus haut). Probablement à réserver aux pilotes avec le niveau de capacité le plus élevé au départ (toi en premier), vu la complexité (itinéraire, devis, escales).

Phase 5 — Admin redevient site-administration

Une fois 3 et 4 en place et utilisés : /admin/reservations/new* peut être retiré ou gardé en secours. /admin/reservations (le tiroir) et /admin/vols (vue flotte) restent probablement utiles comme vue de supervision transverse — à décider si c'est de la « gestion » (reste admin) ou si ça doit aussi migrer.

En parallèle, avant d'étendre les pouvoirs pilote

Corriger la fuite ActionFooter/viewerRole — sinon chaque nouvelle capacité pilote agrandit une fenêtre déjà ouverte.

Décisions à prendre avant de coder

  1. Phase 1 : fusionner tes deux comptes en un seul avec double casquette, ou juste changer le routing pour qu'un compte pilote actif accède aussi à /admin s'il est admin (et vice-versa) sans toucher aux comptes existants ? (Techniquement plus simple : la deuxième option, aucune migration de données utilisateur.)
  2. Qui d'autre que toi aura un jour peut_creer_reservations=true ? Pas besoin de trancher aujourd'hui, mais ça cadre si la colonne doit être un simple booléen ou prévoir plus de nuance dès le départ.
  3. Vol sur mesure côté pilote : réservé à toi seul pour commencer, ou ouvert à tout pilote avec le niveau de capacité le plus élevé dès la Phase 4 ?
  4. Ordre réel de priorité : la Phase 1 (ton confort perso) peut se faire seule, indépendamment du reste, si tu veux un gain rapide avant d'attaquer les phases 2-4 qui sont plus lourdes.
